# Engineering Principles for Self-Mutating Agent Harness Rebuild

Rebuilding a Python self-mutating agent harness into a world-class open-source library for Databricks.

**Domain:** An optimizer LLM mutates a runtime agent's prompts/skills/code; evaluates on a golden set; promotes winners.

---

## 1. DOMAIN MODELING OUTPUT

**File structure:** Root `CONTEXT.md` + `docs/adr/` for hard-to-reverse decisions (per `/mattpocock-skills/engineering/domain-modeling/SKILL.md`).

### 1.1 Key Terms to Pin Down (CONTEXT.md)

Create `/CONTEXT.md` with these domain concepts:

```md
# Agent Optimizer Context

A harness that evolves an agent's behavior by mutation and evaluation.

## Language

**Agent**
A runtime system (prompts, skills, code) that solves a task given an input.
_Avoid_: Model, system, LLM.

**Mutation**
A proposed change to an agent (prompt rewrite, skill replacement, code edit) generated by the optimizer LLM.
_Avoid_: Modification, update, patch.

**Candidate**
An agent in a particular state after one or more mutations applied.
_Avoid_: Version, variant, iteration.

**Golden Set**
A curated collection of inputs with known-good outputs, used to evaluate candidates.
_Avoid_: Test set, benchmark, validation set.

**Evaluation**
Scoring a candidate against the golden set, comparing output quality to known-good results.
_Avoid_: Assessment, testing, judging.

**Promotion**
Moving a candidate into the base agent because it outperformed the previous best.
_Avoid_: Merging, committing, deployment.

**Rollback**
Reverting a candidate back to its parent agent if evaluation fails or performance degrades.
_Avoid_: Undo, restore, revert.

**Optimizer**
The LLM that proposes mutations, given the agent state and evaluation feedback.
_Avoid_: Suggester, planner, generator.
```

**Rationale:** These terms distinguish this domain from generic LLM/ML vocabulary. Mutation ≠ modification (it's reversible, experimental). Candidate ≠ version (only the winner becomes the next base). Golden set ≠ test set (it's finite, curated, high-fidelity, not a distribution sample).

### 1.2 Cross-Context Relationships (if multi-context)

If you later split into Optimizer, Evaluator, Harness contexts, create a root `CONTEXT-MAP.md`:

```md
# Context Map

## Contexts

- [Harness](./src/harness/CONTEXT.md) — runtime execution of agents
- [Optimizer](./src/optimizer/CONTEXT.md) — generation of mutations
- [Evaluator](./src/evaluator/CONTEXT.md) — scoring candidates against golden set

## Relationships

- **Harness → Evaluator**: Harness executes a candidate; Evaluator compares outputs to golden set
- **Optimizer → Harness**: Optimizer generates mutations; Harness applies them to create candidates
- **Evaluator → Optimizer**: Optimizer receives evaluation scores and uses feedback to propose next mutations
```

### 1.3 ADRs for Load-Bearing Decisions

File: `docs/adr/0001-immutable-agent-snapshots.md`

```md
# Immutable Agent Snapshots

**Decision:** Agent state (prompts, skills, code) is immutable once created. Mutations always produce a new snapshot rather than mutating in place. Parents are never overwritten.

**Why:** (1) Every candidate's lineage is traceable; (2) rollback is trivial (hold a reference); (3) concurrent mutation proposals don't interfere.

**Consequences:** Storage grows with mutation count. Solved by snapshot deduplication (store diffs, not full copies). Worth the trade-off for auditability and safety.
```

File: `docs/adr/0002-evaluation-is-sandboxed.md`

```md
# Evaluation is Sandboxed

**Decision:** Candidates run in isolated execution environments. A candidate cannot modify external state (files, databases, APIs) during evaluation.

**Why:** (1) Prevents side-effect attacks if a candidate is adversarial; (2) repeatable evaluation regardless of execution order; (3) no cleanup needed between evals.

**Considered Options:** 
- Sandboxing per candidate (chosen) vs per-mutation (overkill) vs no sandboxing (risky)

**Consequences:** Evaluation setup cost. Mitigated by reusable containers/processes. Worth it for safety.
```

File: `docs/adr/0003-golden-set-is-fixed-per-run.md`

```md
# Golden Set is Fixed Per Optimization Run

**Decision:** The golden set does not change mid-run. All candidates in a run are evaluated against the same ground truth.

**Why:** Prevents chasing a moving target. Optimization converges to the golden set that was locked at start-of-run.

**Consequences:** To update the golden set, start a new run. Old runs' evaluations are not re-computed. Intentional — allows comparing "how well did optimizer X do on golden set Y".
```

(Offer ADRs only when ALL three conditions are met: hard to reverse + surprising without context + result of real trade-off. Per `/mattpocock-skills/engineering/domain-modeling/ADR-FORMAT.md`.)

## 2. CODEBASE DESIGN RULES

Reference: `/mattpocock-skills/engineering/codebase-design/SKILL.md` + `DEEPENING.md` + `DESIGN-IT-TWICE.md`.

### 2.1 Core Principles: Deep Modules at Seams

**Vocabulary (use exactly — no substitutes):**

- **Module:** Function, class, package, or tier-spanning slice with an interface and implementation.
- **Interface:** Type signature + invariants + ordering constraints + error modes. What a caller must know to use it.
- **Seam:** The boundary where a module's interface lives; where you can alter behavior without editing in that place.
- **Adapter:** A concrete thing that satisfies an interface at a seam.
- **Depth:** Behavior per unit of interface learned. Deep = lots of behavior behind small interface (good). Shallow = interface as complex as implementation (bad).

**The Rule:** "Small interface + lots of implementation = depth. Depth produces leverage for callers and locality for maintainers."

### 2.2 Module Boundaries for Agent Harness

**Layer 1: Harness Core (deep, one interface)**

```python
class Agent:
    """Immutable agent snapshot."""
    def __init__(self, prompts: Dict[str, str], skills: Dict[str, Skill], code: CodeModule):
        self.prompts = prompts  # Frozen
        self.skills = skills    # Frozen
        self.code = code        # Frozen
    
    def execute(self, input_dict: Dict) -> Dict:
        """Run this agent on an input. Returns output."""
        # Hides all execution complexity: prompt injection, skill routing, 
        # code execution, error handling, timeouts, resource cleanup.
```

**Why deep?**
- Callers see one method: `execute(input) -> output`.
- Hides: prompt templating, skill dispatch, code sandboxing, error handling, retry logic, resource cleanup.
- Tests call `execute()` directly; they don't care what's inside.

**Layer 2: Mutation Generator (port + adapters)**

```python
class MutationPort:
    """Abstract mutation generator."""
    def propose(self, agent: Agent, feedback: EvaluationResult) -> Mutation:
        raise NotImplementedError

class LLMAdapter(MutationPort):
    """Uses Claude/GPT to propose mutations."""
    def __init__(self, client: LLM):
        self.client = client
    
    def propose(self, agent, feedback):
        # Calls LLM, parses response, returns Mutation

class MockAdapter(MutationPort):
    """Deterministic, for testing."""
    def propose(self, agent, feedback):
        # Returns canned mutations
```

**Why ports + adapters?**
- Optimizer logic is one thing; LLM invocation is another.
- Tests use `MockAdapter`; production uses `LLMAdapter`.
- The real logic sits in one place; transport swaps.

**Layer 3: Evaluator (sandboxed, one interface)**

```python
class Evaluator:
    """Scores a candidate against the golden set."""
    def __init__(self, golden_set: GoldenSet, sandbox_env: SandboxEnv):
        self.golden_set = golden_set
        self.sandbox = sandbox_env
    
    def evaluate(self, candidate: Agent) -> EvaluationResult:
        """Returns (score, per_case_results, errors)."""
        # Hides: sandboxing, parallel execution, timeout enforcement, 
        # diff computation, scoring logic.
```

**Why deep?**
- One method: `evaluate(candidate) -> result`.
- Hides all the machinery: case-by-case execution, comparison, scoring.

### 2.3 Dependency Direction

**Rule:** Core → Ports, never Ports → Core.

```
┌─────────────────────────────────────┐
│  Harness (Agent.execute)            │
│  Evaluator (evaluate)               │
│  Optimizer (run_optimization_loop)  │
└─────────────────────────────────────┘
         ↑           ↑           ↑
         │           │           │
      Mutation    Executor    Sandbox
      Adapters    Adapters    Adapters
```

- Core modules don't import adapters.
- Adapters are leaf nodes; they import ports and core.
- Orchestrator (main/CLI) imports everything and wires up.

### 2.5 What Belongs in Core vs Adapters

**Core:**
- `Agent`, `Evaluator`, `Optimizer` (business logic)
- Mutation types (`PromptMutation`, `SkillMutation`, `CodeMutation`)
- `GoldenSet`, `EvaluationResult` (data model)
- Ports (abstract interfaces)

**Adapters:**
- Executor implementations (subprocess, Docker, Kubernetes)
- Sandbox implementations (chroot, container, process isolation)
- LLM integrations (Anthropic, OpenAI, local)
- Persistence backends (filesystem, S3, database)

**Orchestrator:**
- Wires ports to adapters
- Runs the main loop
- CLI argument parsing

### 2.6 Testability-Driven Design

From `/mattpocock-skills/engineering/codebase-design/SKILL.md`:

1. **Accept dependencies, don't create them:**

```python
# GOOD: Testable
def evaluate(candidate: Agent, executor: ExecutorPort, sandbox: SandboxPort) -> EvaluationResult:
    pass

# BAD: Hard to test
def evaluate(candidate: Agent) -> EvaluationResult:
    executor = DockerExecutor()  # Locked to Docker
    sandbox = ChRootSandbox()    # Locked to chroot
```

2. **Return results, don't produce side effects:**

```python
# GOOD: Testable
def run_optimization_loop(optimizer: MutationPort, evaluator: Evaluator) -> BestCandidate:
    # Returns the winner, doesn't write to disk

# BAD: Hard to test
def run_optimization_loop(optimizer: MutationPort, evaluator: Evaluator) -> None:
    # Writes best agent to `/tmp/best.pkl` — tests must clean up after
```

3. **Small surface area:**

```python
# GOOD: Few methods, simple params
class Evaluator:
    def evaluate(self, candidate: Agent) -> EvaluationResult: pass

# BAD: Many methods, high coupling
class Evaluator:
    def set_golden_set(self, gs): ...
    def set_sandbox(self, s): ...
    def configure_timeout(self, t): ...
    def evaluate_case(self, agent, case): ...
    def get_score(self): ...
    def save_results(self, path): ...
```

## 3. TDD WORKFLOW FOR THIS PROJECT

Reference: `/mattpocock-skills/engineering/tdd/SKILL.md` + `tests.md` + `mocking.md`.

### 3.1 What a Good Test Is

From `/mattpocock-skills/engineering/tdd/tests.md`:

**Good test:** Verifies behavior through public interfaces. Survives refactors. Reads like a specification.

```python
# GOOD: Describes WHAT, not HOW
def test_agent_can_answer_simple_question():
    agent = Agent(prompts={"qa": "Answer: {input}"}, skills={}, code=...)
    result = agent.execute({"input": "What is 2+2?"})
    assert "4" in result.get("output", "").lower()

# BAD: Tests implementation details
def test_agent_calls_prompt_formatter():
    agent = Agent(...)
    with patch('agent.PromptFormatter.format') as mock_fmt:
        agent.execute({"input": "test"})
        assert mock_fmt.called  # ← Tests plumbing, not behavior
```

**BAD anti-patterns:**
- Implementation-coupled: mocks internal collaborators.
- Tautological: expected value restates the code logic.
- Horizontal slicing: all tests first, then all implementation.

### 3.2 Seams — Where Tests Go

**Seam = public boundary you test at.**

Before writing any test, confirm seams with the user:

- **Seam 1:** `Agent.execute(input_dict) -> output_dict` — integration tests
- **Seam 2:** `Evaluator.evaluate(candidate) -> EvaluationResult` — integration tests
- **Seam 3:** `MutationPort.propose(agent, feedback) -> Mutation` — unit tests for each adapter
- **Seam 4:** `Mutation.apply(agent) -> Agent` — unit tests for mutation types
- **Seam 5:** Optimizer loop orchestration — integration tests

Test only at pre-agreed seams. You can't test everything — agree upfront which paths matter.

### 3.3 Rules of the Loop

From `/mattpocock-skills/engineering/tdd/SKILL.md`:

1. **Red before green:** Write the failing test first.
2. **One slice at a time:** One seam, one test, one minimal implementation per cycle.
3. **Refactoring is not part of the loop:** Belongs to the review stage, not red → green.

```python
def test_prompt_mutation_applies_and_returns_new_agent():
```

**Week 3: Evaluator Seam**

```python
# RED: Test Evaluator.evaluate() scores correctly
def test_evaluator_compares_candidate_output_to_golden_set():
    golden = GoldenSet(cases=[
        GoldenCase(input={"q": "2+2?"}, expected_output="4")
    ])
    evaluator = Evaluator(golden_set=golden, executor=MockExecutor())
    candidate = Agent(...)
    
    result = evaluator.evaluate(candidate)
    
    assert result.passed_cases == 1
    assert result.total_cases == 1
    assert result.score == 1.0

# GREEN: Implement Evaluator.evaluate()
class Evaluator:
    def evaluate(self, candidate: Agent) -> EvaluationResult:
        passed = 0
        for case in self.golden_set.cases:
            output = candidate.execute(case.input, executor=self.executor)
            if self._matches(output, case.expected):
                passed += 1
        return EvaluationResult(passed_cases=passed, total_cases=len(self.golden_set.cases), ...)
```

**Week 4: Mutation Port + Adapters**

```python
# RED: Test LLMAdapter generates valid mutations
def test_llm_adapter_proposes_mutations():
    adapter = LLMAdapter(client=MockLLM(returns={"mutation_type": "prompt", ...}))
    agent = Agent(...)
    feedback = EvaluationResult(score=0.5, failed_cases=[...])
    
    mutation = adapter.propose(agent, feedback)

    def propose(self, agent: Agent, feedback: EvaluationResult) -> Mutation:

        response = self.client.generate(prompt)
```

**Week 5: Optimization Loop Integration**

```python
# RED: Test full optimization loop
def test_optimization_loop_runs_and_improves_score():
    golden = GoldenSet(cases=[GoldenCase(...), ...])
    base_agent = Agent(prompts={"qa": "broken"}, ...)
    optimizer = MockOptimizer(mutations=[PromptMutation(...)])  # Pre-canned
    evaluator = Evaluator(golden_set=golden, executor=MockExecutor())
    
    harness = OptimizationHarness(base_agent, optimizer, evaluator)
    final_agent = harness.run(max_iterations=1)
    
    initial_score = evaluator.evaluate(base_agent).score
    final_score = evaluator.evaluate(final_agent).score
    assert final_score > initial_score

# GREEN: Implement OptimizationHarness.run()
class OptimizationHarness:
    def run(self, max_iterations: int) -> Agent:
        best_agent = self.base_agent
        best_score = self.evaluator.evaluate(best_agent).score
        
        for i in range(max_iterations):
            feedback = self.evaluator.evaluate(best_agent)
            mutation = self.optimizer.propose(best_agent, feedback)
            candidate = mutation.apply(best_agent)
            candidate_score = self.evaluator.evaluate(candidate).score
            
            if candidate_score > best_score:
                best_agent = candidate
                best_score = candidate_score
        
        return best_agent
```

### 3.5 What NOT to Test

From `/mattpocock-skills/engineering/tdd/mocking.md`:

**Don't mock your own modules.** Mock at system boundaries only:
- External APIs (LLM providers)
- System calls (subprocess, Docker)
- Time/randomness
- Databases (or use test DB)

**Good seams for mocking:**
- `ExecutorPort` — mock with `InMemoryExecutor` for tests
- `MutationPort` — mock with `CannedMutationAdapter` for tests
- LLM client — mock with `MockLLMClient` returning fixed responses
- Sandbox — mock with `UnsandboxedExecutor` for fast tests

**Don't mock:**
- `Agent` (it's yours — test it directly)
- `Mutation` types (test them directly)
- `Evaluator` (it's yours)

> "You've said mutations are immutable. I want to push on that:
>
> **Q1:** If a user runs 1000 optimization iterations, do you store 1000 full agent snapshots? Or do you deduplicate by storing diffs?
>

## 6. SKILL INVOCATION ORDER FOR MULTI-WEEK REBUILD

**Week 1: Architecture & Domain**

1. **`/grilling`** — Stress-test domain concepts and architectural decisions with the user.
   - Q: What does "immutability of agents" actually mean? (Snapshots? Diffs? Cache?)
   - Q: How does rollback work if something goes wrong mid-eval?
   - Q: Can two mutations run in parallel, or are they sequential?

2. **`mattpocock-skills:domain-modeling`** — Pin down terminology, create CONTEXT.md + ADRs.
   - Output: `/CONTEXT.md`, `/docs/adr/0001-*.md`, etc.
   - Ensures the team has the ubiquitous language locked.

3. **`mattpocock-skills:codebase-design`** — Lay out module boundaries, seams, interfaces.
   - Output: Module structure, deep-module diagram, dependency graph.
   - Use `DESIGN-IT-TWICE.md` if multiple interface options exist.

**Week 2: TDD Red-Green-Refactor Cycles**

4. **`mattpocock-skills:tdd`** — Follow the red → green loop to build core types + seams.
   - Start with: `PromptMutation`, `Agent.execute()`, `Evaluator.evaluate()`.
   - Output: Tests + passing implementation.

**Weeks 3–4: Integration & Adapters**

5. **`mattpocock-skills:prototype`** — If the state machine or mutation logic is unclear, build a throwaway logic prototype.
   - Use `LOGIC.md` branch if the question is "does this state model actually work?"
   - Output: Validated reducer/state machine that can be lifted into real code.

6. **`mattpocock-skills:diagnosing-bugs`** — If tests fail or behavior diverges from spec, use the 6-phase diagnostic loop.
   - Phase 1: Build a tight feedback loop (failing test or curl script).
   - Phase 2–6: Reproduce, minimise, hypothesize, instrument, fix.

**Week 5: Review & Finalize**

7. **`mattpocock-skills:code-review`** — Two-axis review before merge (Standards + Spec).
   - Have a sub-agent review against CODING_STANDARDS.md.
   - Have another sub-agent verify the spec (requirements) is met.

8. **`mattpocock-skills:research`** — If you need to research best practices (e.g., sandbox implementations, LLM integration patterns), spin up a background research agent.
   - Output: Single Markdown file with findings, cited to sources.

9. **`mattpocock-skills:resolving-merge-conflicts`** — If multi-week work creates conflicts, use this to preserve both intents.

## 8. RULES THAT MUST BE FOLLOWED (NOT GUIDELINES)

From your `CLAUDE.md`:

3. **`/compact` at 50% context.** Check with `/context`.
4. **Subagents for parallelizable work.** Code review runs two axes in parallel (Standards + Spec). Grilling can happen in parallel with research.
5. **Verify before declaring done.** Run all tests, check types, confirm behavior matches spec.
6. **End session with `/retro`.** Reflect on what worked, distill into memory.
